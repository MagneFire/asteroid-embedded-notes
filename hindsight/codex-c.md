**Yes for bring-up. My verdict is stay-but-change:** retain the proven C/assembly hardware layer and libraries; prefer safe Rust for new parsers and application state.

C reduced simultaneous unknowns. It made lk/lk2nd/vendor register sequences directly comparable and integrated TinyUSB, NimBLE and mbedtls with little language glue ([Makefile](/Users/darrel/Downloads/AsteroidOS/asteroid-embedded/Makefile:20)). Following the downstream I2C sequence—not changing languages—unblocked touch. GCC, explicit assembly and the flat ELF made bring-up straightforward. The fault records and `addr2line` tooling are valuable, although equally usable with Rust debug information ([exceptions.c](/Users/darrel/Downloads/AsteroidOS/asteroid-embedded/src/soc/exceptions.c:1), [run.py](/Users/darrel/Downloads/AsteroidOS/asteroid-embedded/tools/run.py:46)).

**The fix history mostly supports C’s practicality, rather than indicting its safety.** GIC trigger configuration (`9217a14`), IRQ stack alignment (`9595e4e`), PLL sequencing (`fde97a9`) and cache erratum barriers (`385f63d`) would still require correct hardware knowledge in Rust. Duplicate handler registration (`be64200`) is also a logic bug. The GPU/CPU race fixed during `f18b970` required waiting before scanning layers; Rust would help only through an API encoding ownership until fence completion ([GPU-UI.md](/Users/darrel/Downloads/AsteroidOS/asteroid-embedded-notes/GPU-UI.md:406)).

C’s ongoing cost is manual bounds, lifetime and arithmetic reasoning. Concrete current hazards include negating `INT_MIN` in [fmt.c](/Users/darrel/Downloads/AsteroidOS/asteroid-embedded/src/lib/fmt.c:48) and overflow-prone `wn + 4` validation in [i2c_qup.c](/Users/darrel/Downloads/AsteroidOS/asteroid-embedded/src/soc/i2c_qup.c:214). These are inspection findings, not recorded overflow fixes. Safe slices and ownership prevent memory violations; explicit checked arithmetic remains necessary in release Rust. IRQ-shared queues also deserve synchronization contracts beyond `volatile`.

The FFI seam is manageable but increasingly expensive: raw pointers/lengths, duplicated constants and globally manufactured mutable references ([watch.rs](/Users/darrel/Downloads/AsteroidOS/asteroid-embedded/ui/src/watch.rs:28)). Generate declarations, document buffer lifetimes and enforce main-loop-only access. The 2,000× division slowdown from Rust builtins/link order demonstrates real integration overhead ([notes](/Users/darrel/Downloads/AsteroidOS/asteroid-embedded-notes/EMBEDDED.md:452)).

A Rust-led design is viable: [Armv7-A has Tier-2 `no_std` support](https://doc.rust-lang.org/rustc/platform-support/armv7a-none-eabi.html), and [Embassy supports AArch32](https://github.com/embassy-rs/embassy/blob/main/embassy-executor/src/platform/aarch32.rs). I would start with a superloop, typed peripheral ownership, bounded queues and isolated unsafe MMIO/cache/SCM code. Expect custom Qualcomm integration: replacing TinyUSB requires a [USB driver implementation](https://docs.embassy.dev/embassy-usb-driver/git/default/trait.Driver.html); [TrouBLE supports UART HCI](https://github.com/embassy-rs/trouble), but Broadcom patchram, bonding and phone interoperability still need validation. Typed PM4 builders could improve GPU code; command correctness remains hardware-specific.

C++ offers RAII with easy C reuse but little automatic memory safety. Zig offers checked operations in safety-enabled builds, but [checks depend on build mode](https://ziglang.org/documentation/master/#setRuntimeSafety); I see insufficient benefit to introduce another language.

Avoid a wholesale rewrite: its cost includes revalidating boot, suspend, USB, BLE and rendering. Incrementally move new protocol/application modules into the existing Rust build. Strengthen C with checked lengths and sanitizer-backed parser tests; today `make test` covers only console/ADB. Also, the current tree already GPU-paints rectangles, glyphs and images (`d36168e`), beyond composition alone.
