# Review, fixes and application overhaul for aod-display-rest

## Context

Review of the 6 commits on `aod-display-rest` (main...HEAD, 525 lines) and the
uncommitted power harness (1,171 lines), by my own read, an independent read, Codex and
Astra (both read-only, static). Nothing was built or run. No high-severity bugs; the worst
are error paths on stuck hardware, and one harness bug that skews measurements.

Decisions so far: the harness stays separate, and all new work goes in a new worktree.
Promoting the sleep measures to production is a later job.

Overhaul verdict, shared with Codex: a complete rewrite is not justified. The superloop,
drivers, Slint views and rendering are sound, and the 2026-10-31 series already moved
power, clock apps and console execution out of the loop. What remains is coordination in
`main()`, so Phase 2 is a staged refactor of that, and it needs its own go-ahead. Phase 3
then replaces the polling loop itself with an event-driven scheduler, not an RTOS.

## Where the work happens

New worktree `../asteroid-embedded-review`, branch `aod-review` off 84fbbe3. The main

## Findings: harness

Fix these in the re-applied patch, not on the branch.

- **H1 (medium, skews measurements):** the plug-in path in `powertest_poll` calls
  `powertest_measures(0)`, which sets `usb_hold_up`. USB then doesn't rest after later
  unplugs until a mask with U runs: about 4 mA on later `dsi` or default runs and on the
  settle of sleep runs in the same boot. Arms within one run stay comparable. Fix:
  `powertest_measures(PT_USB)`.
- **H2 (low):** `touch_rmi4_rail` clears `rail_off` before `rmi4_init()`, so a failed init
  can't be retried; an RPM failure on the way off leaves attention masked.
- **H3 (low):** the console's `emmc_init` ignores `card_asleep` and `vcc_off`.
- **H4 (low, from Codex, read in the diff):** `panel_rails` sets `rails_off` even when the
  requests failed, and `hub_services` counts requests sent, not acknowledged. So
  `want == have` doesn't prove physical state.
- **H5 (from Astra, confirmed):** sleep, floor and night schedules ask for bits sparrow can't
  provide, so `want != have` causes endless retries, and `hub_ready()` reads STM32 state on
  sparrow. Add per-board measure masks and dispatch `hub_ready` through the hub driver.
- `pt_usb_undo` has no reader, so the "undo it after 10 s" comment is false. Remove it.

## Open points

- **Always-on after unplug is one-way.** `power.c:153,223` handles leaving always-on only.
  With nightstand always-on off and normal always-on on, the screen stays dark after
  unplugging until the next wake. Plan: narrow the comment. Codex notes that only
  documents the gap, so say if you want the entry path added.
- **Sparrow's panel-on clamp path is unproven.** All 11 arms in its collapse log are
  `aod=off`, and matching lane maps don't validate the sequence. The open "reset while
  plugged in and asleep" would run this path if the nightstand always-on face was on.
  That is a lead, not a diagnosis.
- **Trim cost is unmeasured.** 64 conversions every 300 s; about 640 ms is the wait bound,
  excluding SPMI overhead. Log the duration in the harness.

## Phase 2: application overhaul (staged, needs its own go-ahead)

**Problem:** `main()` is about 550 lines with some 20 locals as implicit state. It picks
sensor activity from UI getters (`main.c:478`), dispatches app actions (`:628`), does half
the sleep transition (`:699`), renders (`:729`) and assembles deadlines (`:886`). Every
wake runs the whole pass, and a pass on the sleep clock takes over 100 ms.

**Target:** keep one superloop, the drivers, Slint views, gestures, rendering and the Rust
copied-data event boundary (`ui/src/watch.rs`). Add three things, using direct calls and
the existing serial counters, with no message framework:

- an application controller for commands and state, shared by UI and console;
- a presenter that pushes changed values to the UI;
- a power coordinator owning display and sensor needs and transition order.

Services expose a bounded `poll(now)`, a next deadline and sleep blockers.

**Stages, each independently testable:**

1. Extract boot, diagnostics and presentation with no order change; compare boot logs and
   frame counts.
2. Route UI and console actions through shared controller functions; host tests for
   identical effects and persistence.
3. Split pure power decisions from hardware effects, so `power.c` gets a host test with
   fake time: ordering, simultaneous wake and sleep, notification wakes, dropped wake
   touches, the full AOD and nightstand setting matrix.
4. Centralise deadlines, including BMS and console jobs, which BMS gets only by incidental
   polling today (`bms.c:842`). Then skip services with nothing due while asleep. This is
   the stage with a power payoff, so A/B it.
5. Board capabilities for panel power and reset, removing `lines == 434`-style checks, so
   a third board adds data and driver ops, not application branches.

**Risks:** reordering can break GPU and cache ownership, AOD sequencing, gesture retention,
console cancellation and settings durability, so each stage states what it preserves. The
harness touches `main.c`, `display.c` and `usb.c`, so it needs re-porting per stage. Power
gain comes from stage 4 only, and has to be measured.

## Phase 3: moving away from the superloop (after Phase 2, needs its own go-ahead)

**Recommendation:** if the gate below passes, replace the polling pass with an event-driven,
run-to-completion scheduler on the same single stack, rather than a preemptive RTOS. Astra
agrees it's the best fit, conditionally. Phase 2 stays the first
step either way: its `poll`, next-deadline and blocker interface is what the scheduler
schedules. This reverses the 2026-10-25 "raw superloop" decision, so record it in the notes.

**Gate:** the strongest argument against Phase 3 is that Phase 2's deadline-driven polling
already captures much of the benefit, while the same blocking handlers still set worst-case
latency. So decide after Phase 2 stage 4, on measured energy and worst-case latency.

**What ties the code to one context today:**

- NimBLE's port runs everything in main-loop context, with no locking (`src/bt/npl.c`).
- TinyUSB uses `OPT_OS_NONE`, and Slint is `unsafe-single-threaded`.
- Interrupts mostly just fill rings, which suits events, though the touch I2C chain does
  run in IRQ context.
- Three nested pumps are a hand-made scheduler already: `pp_wait` calls `usb_poll`, adb
  drain calls `usb_poll`, and NPL waits call `hci_poll`. The first caused the re-entry bug
  the console queue was built to fix (`bright` re-entering `tud_task`).
- About 33 `delay_ms` calls block everything, up to 120-255 ms for panel sequences, and
  hub resets and firmware loads longer.

**Options:**

| Option | Gains | Costs | Verdict |
|---|---|---|---|
| Event-driven run-to-completion: IRQs set flags, one deadline queue, run only what's due, idle otherwise | No per-pass polling; tickless awake; deadlines in one place; every stack above fits unchanged | Long blocking sequences still need splitting | **Recommended** |
| Same, plus one cooperative worker context with its own stack for slow sequences | `delay_ms` yields, so panel, hub and firmware sequences stop stalling input and USB; `pp_wait`'s and adb's pumps can go | A context switch; yield points are new re-entry hazards, needing ownership and cancellation rules. NimBLE's semaphore waits still need transport progress, so that pump stays | Add only if stalls still matter after stage 3 |
| Preemptive RTOS (FreeRTOS, Zephyr) | Priority responsiveness; blocking code stays simple | Shared SPMI, I2C, log and settings need locks or single-owner tasks; custom cluster-collapse idle and watchdog hooks; new races; every port here assumes one context | No: the responsiveness doesn't justify re-proving the ports and sleep path |
| Rust async (Embassy) | Typed tasks, no hand-written state machines | No MSM8226 collapse integration; blocking C drivers don't become async; C stacks stay behind FFI | No. Astra says upstream now has a Cortex-A executor (not checked by me), but that isn't the blocker |

**Power, honestly:** unknown. The 99.94% VDD-min figure is from a stripped sturgeon harness
run, not production. Cluster wakes already restore full CPU speed, and AOD drawing and BT work
boost it, so only non-cluster passes run on the slow clock. The 136-140 mA awake figure has no
breakdown, so the 1 ms tick's share is unknown. Adding deadlines that are implicit today could
even raise wake frequency. Stage 1 measures energy and clock state before anything moves.

**Stages:**

1. Measure: per-wake active time, clock state and time per service, BT connected and AOD
   on, plus worst-case blocked latency. Inventory every implicit deadline: Slint timers,
   gesture and rotation animation, haptics, inactivity, recovery. If a pass is a small
   share of energy, the case rests on latency and structure alone.
2. Add the scheduler alongside the loop: event flags set by IRQs, one deadline queue with
   host tests for wrap, starvation and saturation. Design atomic flag consumption, queue
   overflow and re-queueing partly drained work. The pending-event check must cover every
   idle path (`spm_idle`'s masked section and unmasked fallback, the awake `wfi()`), or an
   event can be lost just before sleep.
3. Move services one at a time, cheapest first: settings, weather, notifications, charger
   and BMS, touch, hub, BT, USB. The loop shrinks until only idle remains. Keep the 1 Hz
   cable check, as unplug has no interrupt (rising edge only).
4. Add a display-done interrupt (completion is register polling today), then drop the 1 ms
   tick once the deadline inventory is covered. Feed the watchdog from a liveness check across services, not from each pass.
5. Only if stalls remain: the worker context, moving panel, hub and firmware sequences
   onto it and removing the pumps.

**Risks:** a lost wakeup is the main new failure, and it looks like a hung watch, so stage 2
needs the race covered first. Run-to-completion gives no protection against a slow handler,
so each service gets a time budget logged in debug builds. Watchdog semantics change.
Sleep-path changes need night runs, rehearsed with 1-minute arms. Have Codex review the
design before stage 2.
