# PNI EM7184 (SENtral) sensor hub on sparrow

Protocol as the downstream Linux driver uses it. Sources, all from the Android kernel
`android-msm-sparrow-3.10-marshmallow-mr1-wear-release` @ 3d2fa521 (copies here):

- `sentral-iio.c` (`drivers/sensors/pni/`) and `sentral-iio.h` (`include/linux/`): **the
  driver sparrow runs**. `sparrow_user_msm8226-perf_defconfig` and
  `sparrow_userdebug_msm8226_defconfig` set `CONFIG_SENSORS_SENTRAL_IIO=m` and leave
  `CONFIG_SENSORS_EM718X` unset; the system image ships `/system/lib/modules/sentral-iio.ko`.
  The DTS node is `compatible = "pni,em7184"` (sentral-iio.c:3304).
- `em718x_core.c` / `em718x_main.c`: the older generic EM718x host driver (EM7180 register
  map, `compatible = "pni,em718x"`), not built for sparrow. Only useful for the meaning of
  registers both maps share (chip status bits, upload address, ROM/RAM version).
- `bmd101.c` (`drivers/sensors/`): see "Heart rate" below.
- HAL: `system/lib/hw/sensors.sparrow.so` from `downloads/system-sparrow-m.tar.gz` on pc
  (strings and its `sensor_t` table, parsed offline).

## Bus, pins, power

- I2C BLSP1 QUP2 (`i2c@f9924000`, gpio 6 SDA / 7 SCL, function 3, 2 mA, no pull),
  address 0x28, `qcom,i2c-bus-freq = <400000>` (sparrow_pr_msm8226.dtsi:1000-1013,
  board-8226-gpiomux.c:179 `gpio_i2c_config`). The firmware header's I2C clock field is 2
  (meaning not documented in the sources).
- Interrupt: msmgpio 111, `interrupts = <111 0x1>`, requested `IRQF_TRIGGER_RISING |
  IRQF_ONESHOT` as a threaded handler (sentral-iio.c:3211-3213), `enable_irq_wake`
  (3225-3227). The gpio is requested as a plain input (3136-3145), no pull set. Whether the
  line is a level held until the FIFO is read or a pulse is not visible in the driver.
- No reset gpio, no regulator in the node: the hub is powered by the board and only reset
  through its own reset register.
- SMBus-style accesses: byte write/read, block write `[reg, data...]`, block read
  `[reg]` + repeated start + read (sentral-iio.c:46-127).

## Reset and firmware upload (sentral-iio.c:1426-1535, 2865-2902)

1. Image check: header (h:535-550, 16 bytes LE): u16 signature 0x652A, u16 flags (bit0
   EEPROM-no-exec, bits 8-10 I2C clock, bits 11-14 ROM version expected), u32 text CRC,
   u32 reserved, u16 text length, u16 reserved. `16 + text_length <= size`. A 44-byte CDS
   block ends the text (signature 0xC88B, u16 RAM version, CDS version, boot protocol, pin
   and pull selections, 16-byte name; h:552-561), not used by the driver beyond the pointer.
2. Write `RESET_REQ = 1`. **No wait follows**: the next access is the read-modify-write of
   CHIP_CONTROL. (em718x waits for the interrupt, then polls CHIP_STATUS every 50 ms for
   `idle && (upload done | upload error | no EEPROM)`, up to 4 s: em718x_core.c:2082-2154.)
3. CHIP_CONTROL |= 0x02 (upload enable), read-modify-write, skipped if already set
   (1348-1406).
4. Data = everything after the 16-byte header, in writes to 0x96 of
   `MIN(RAM_BUF_LEN 64, I2C_SMBUS_BLOCK_MAX 32)` = **32 bytes**; each 32-bit word is
   byte-swapped (`swab32`): the file is little endian, the hub takes big endian
   (1483-1501; em718x_core.c:664 says so). No delay between writes.
5. CHIP_CONTROL &= ~0x02.
6. Read CRC_HOST (4 bytes LE) and compare with the header's text CRC; mismatch = failure.
   (The error message has expected/got swapped, 1520-1524.) This is the only "upload done"
   signal: there is no status poll.
7. `mdelay(100)`, CHIP_CONTROL |= 0x01 (CPU run), `init_complete`, `mdelay(100)`, then a FIFO
   read (2884-2898). The firmware then sends a meta event **Initialized** (16), on which the
   driver sets the FIFO watermark and rewrites every enabled sensor's config and the step
   count init (958-963, 425-457): sensor configuration only sticks after Initialized.

`em7184.fw` here: 22028 bytes, signature 0x652A, flags 0x0A00 (no-exec 0, I2C clock 2, ROM
version expected 1), text CRC 0xFE09F79B, text length 22012 (= file - header, a multiple of
4), CDS RAM version 0x237D, CDS version 2, pin selection[0] 6, pull selection ff 3f.
**The CRC is CRC-32/MPEG-2** (poly 0x04C11DB7, MSB first, init 0xFFFFFFFF, no final xor,
no reflection) over the bytes as sent on the bus (the swapped words): checked offline, it
reproduces 0xFE09F79B, so the host can verify the file before uploading.

A crash reset (`sentral_crash_reset`, 705-715) reruns the same work: the firmware is
re-uploaded from scratch.

## Parameter I/O (139-335)

- Read (size <= 16): `PARAM_PAGE = size < 16 ? (size << 4) | page : page`;
  `PARAM_REQ = param`; then up to 20 times: sleep 8-10 ms, read PARAM_ACK until it equals
  `param`; read `size` bytes from 0x3B; finally `PARAM_PAGE = 0`, `PARAM_REQ = 0`.
- Write (size <= 8): `PARAM_PAGE = size < 8 ? (size << 4) | page : page`; block write the
  data to 0x5C; `PARAM_REQ = param | 0x80`; ack poll as above for `param | 0x80`; then
  page 0, req 0.
- Pages (h:267-287): 1 system, 2 algorithm warm start, 3 sensors, 13 algorithm knobs,
  14 ASUS.
  - Page 1: 1 meta event control (u64: per event id `n` bit `2(n-1)+1` = event enabled, bit
    `2(n-1)` = interrupt enabled, 478-506), 2 FIFO control (u16 watermark, u16 size), 3/4
    sensor status banks (8 bytes, one per sensor: data available, i2c nack, device id error,
    transient error, data lost, power mode), 30 host irq timestamp (u32 at irq, u32 current),
    31 physical sensor status (accel/gyro/mag: u16 rate, u16 range, flags).
  - Page 2: params 15-17 accelerometer calibration coefficients, s64 each (2583-2646).
  - Page 3: param `id` = sensor info (16 bytes: type, driver id, driver version, power,
    u16 max range, u16 resolution, u16 max rate, u16 fifo reserved, u16 fifo max, u8 event
    size, reserved; h:451-463); param `id + 31` = sensor config (8 bytes: u16 sample rate,
    u16 max report latency ms, u16 change sensitivity, u16 dynamic range; h:465-470).
  - Page 14: 1 inactivity timeout (u16 s), 2 step count init (u16).

## Sensors: enabling and rates

A sensor runs while its config has a non-zero sample rate; "enable" in the driver only
marks the id for event delivery, "disable" writes rate 0 / latency 0 (587-662). The HAL
(`/sys/class/sensorhub/sentral/{enable,delay_ms,batch,flush}`) sends Android sampling
periods converted per id (2122-2223): ms to Hz (`1000 / MIN(1000, ms)`) for most; the raw
ms value for step counter (19) and sleep (28); seconds for inactivity (30, rate field =
timeout, real rate 1 Hz); `ms / 10000` mapped to a fitness id for coach (29, real rate
30 Hz). A batch with a non-zero rate is preceded by `mdelay(20)`.

Sensor ids (h:188-227) = HAL handles. The sparrow HAL lists: accelerometer 1, gyroscope 4,
gravity 9, linear acceleration 10, game rotation vector 15, gyro uncalibrated 16,
significant motion 17, step detector 18, **step counter 19**, tilt detector 22,
**wrist-tilt gesture 26**, sleep 28, coach 29, inactivity alarm 30, activity 31. No
magnetometer, no heart rate. `sensor_t` values: step counter minDelay 1 s, maxDelay
65535 s, fifoMax 1193, flags 0x2 (on-change); wrist tilt minDelay 33333 us, maxDelay 1 s,
flags 0x7 (wake-up, special); accel/gyro minDelay 5 ms, fifoMax 447. So Android's step
counter reaches the hub as rate field 1000 (the 1 s minimum period, in ms), wrist tilt as
30 Hz [I: what the framework clamps to; not traced].

## FIFO read on interrupt (2773-2806, 1280-1346, 1135-1266)

1. IRQ thread: read WAKE_SRC (0x4D, 1 byte). If it differs from the previous value, each
   2-bit counter that changed gives one wake-up event: wrist tilt (bits 0-1) and
   significant motion (bits 2-3), wrap at 4 (h:97) (907-934).
2. Work: read FIFO_BYTES (u16 LE), then **one** block read of that many bytes from 0x00
   (the hub must wrap its window 0x00-0x31; `SENTRAL_FIFO_BLOCK_SIZE 50` is defined but
   unused), parse.
3. A delayed "watchdog" 2 s after each FIFO read (cancelled by the next IRQ) reads ERROR:
   0x27 stack overflow, 0x30 math, 0x40 memory = crash -> full reset; then CRC_HOST: non-zero
   and different from the upload CRC = crash; then reads the FIFO once more (2808-2852).

Event format: one id byte, then a fixed number of data bytes by id (1147-1236):

| Ids | Data bytes |
|---|---|
| 0 NOP | 0 |
| 17 sig motion, 26 wrist tilt | 0, ignored (counted from WAKE_SRC) |
| 18 step detector, 22 tilt, 23 wake, 24 glance, 25 pick up, 30 inactivity | 0 |
| 21 heart rate, 28 sleep | 1 |
| 5 light, 7 temperature, 8 proximity, 12 humidity, 13 ambient temp, 31 activity | 2 |
| **19 step counter** | 2: u16 LE count, wraps; the driver keeps a 64-bit total, +65536 when the count goes down (1057-1082) |
| 6 pressure, 29 coach | 3 |
| 1 accel, 2 mag, 3 orientation, 4 gyro, 9 gravity, 10 linear accel | 7 (3 x s16 + status) |
| 11, 15, 20 rotation vectors | 10 |
| 14, 16 uncalibrated | 13 |
| 0xF5 debug | 13: attr byte (bits 0-5 length, 6-7 type 0 string/1 binary), 12 bytes (h:574-580) |
| 0xFC / 0xFD timestamp LSW / MSW | 2: u16; hub time = MSW << 16 \| LSW, 31.25 us per tick (h:77) |
| 0xFE meta event | 3: event id, byte 1, byte 2 (h:308-334) |
| other | FIFO corrupt: rest of the read dropped (1236-1241) |

Meta event ids: 1 flush complete (byte 1 = sensor), 2 sample rate changed, 3 power mode
changed, 4 error, 5 mag transient, 6 cal status, 7 stillness, 8 algo slowdown, 9 cal
stable, 11 sensor error, 12 FIFO overflow, 13 dynamic range, 14 FIFO watermark, 15 self
test, 16 initialized. Overflow 5 times (counter cleared on resume and on Initialized) =>
crash reset (976-983).

On Initialized the driver reads FIFO control and sets the watermark to `size - 500` when
the FIFO is larger than 500 bytes, with the watermark meta event enabled and its interrupt
disabled (877-905).

## Suspend and wake (2971-3030)

- Before suspend: HOST_CONTROL |= 0x20 (AP suspended), read-modify-write; wait up to 5 s for
  a pending FIFO read. After resume: clear 0x20, clear the overflow count.
- Nothing else: no standby request (HOST_CONTROL bit0 is never set), no CPU stop. The IRQ
  is a wake source; the wrist-tilt gesture is a wake-up sensor (HAL flags 0x7), and an IRQ
  takes a 250 ms wakeup source while the wake-up counters changed (2795-2796). Which events
  still raise the interrupt with "AP suspended" set is up to the firmware [U]; by Android's
  rules only wake-up sensors (and a FIFO near full) should.

## Step count

- Step count init (page 14 param 2, u16): written with the current low 16 bits on every
  Initialized so a crash reset continues the count (450-455, 369-377).
- Events arrive on change, with the rate field acting as a report interval in ms [I];
  STEP_REPORT (0x4E) reads back a u16 report delay.

## Heart rate

Not on the hub. The protocol has id 21 (1 data byte) but the sparrow HAL lists no heart
rate sensor and the system image has no `android.hardware.sensor.heartrate.xml` (only
step counter/detector and gyroscope permissions). The DTS `bmd101` node (`compatible =
"neurosky, bmd101"`, no resources) is for a NeuroSky BMD101 ECG front end: `bmd101.c`
talks to it over `/dev/ttyHSL1` with reset gpio 55, chip select gpio 53 and regulator
`8226_l28` (bmd101.c:42-63), but `CONFIG_SENSORS_BMD101` is in neither sparrow defconfig, so
it is not built. The ZenWatch 2 has no heart rate sensor; `/system/usr/share/bmd/*.bmd`
in the image are unrelated data files [I].

## For our firmware (hub_em7184.c)

- Synchronous: probe 0x90, upload (checking the file's CRC first), CPU run; from the main
  loop: poll the FIFO until Initialized (2 s cap), then FIFO watermark, step count init,
  step counter config {1000, 0, 0, 0}, 20 ms, wrist tilt config {30, 0, 0, 0}; then the
  rising-edge pin IRQ and MPM pin 54.
- IRQ chain (I2C callbacks): WAKE_SRC -> FIFO_BYTES -> FIFO reads parsed on the fly.
  Our QUP limits a read to the FIFO size, so the FIFO is read in pieces that never cross
  the 50-byte window, each starting at `offset % 50` [U: the vendor reads it in one burst].
- AP suspended set on the first cluster sleep, cleared when the screen wakes (not every
  collapse, which happens each second); while it is set the FIFO is drained once a minute
  for the always-on face's step count.
