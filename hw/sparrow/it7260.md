# ITE IT7260 touch controller (sparrow)

Sources: `it7260_ts_i2c.c` in this directory (the sparrow kernel's
`drivers/input/touchscreen/it7260_ts_i2c.c` @ 3d2fa521, "a mostly complete rewrite" of
ASUS's driver; cited as `vd:<line>`), the DTS copies in `../../dts/android-sparrow/`,
`arch/arm/mach-msm/board-8226-gpiomux.c` and `drivers/i2c/busses/i2c-qup.c` from the
same kernel commit (on pc, `git show 3d2fa521:<path>` in the kernel.msm mirror), and,
as a second opinion only, Qualcomm's later port of the same driver,
`drivers/input/touchscreen/it7258_ts_i2c.c` (also in 3d2fa521, and in
`refs/changes/00/324000/1`; cited as `qc:<line>` from the latter). The firmware draft is
`src/input/touch_it7260.c` on the `sparrow` branch.

## Board wiring

- `sparrow_pr_msm8226-720p-mtp.dtsi:37`: `IT7260@46` on `i2c@f9927000` (BLSP1 QUP5),
  `interrupts = <17 0x2>` (IRQ_TYPE_EDGE_FALLING), `reset = <16>` (a plain u32 read by
  `parse_reset_gpio`, vd:1678). The probe requests the IRQ as
  `IRQF_TRIGGER_FALLING | IRQF_ONESHOT` (vd:1823), threaded, no hard handler.
- QUP5: `qcom,i2c-bus-freq = <384000>`, src 19.2 MHz, SDA gpio 18, SCL gpio 19
  (`sparrow_pr_msm8226.dtsi:1016-1030`). Same pins and speed as sturgeon.
- Supplies: L6 1.8 V (`sparrow_pr_msm8226-regulator.dtsi:257-266`), L19 2.85 V (:400-409)
  and LVS1 (:511-516) are all `regulator-always-on` tagged `//ASUS_BSP "Touch Porting"`.
  The driver itself touches no regulator. Which rail is AVDD and which is I/O is not
  stated (guess: L19 analog, L6 1.8 V I/O, LVS1 the I2C pull-ups as on sturgeon).
- gpiomux (`board-8226-gpiomux.c`, the non-SKUF `msm_synaptics_configs`, installed for
  every 8226 board that is not SKU-F, lines 345-358 / 886): gpio 16 GPIO 6 mA pull-down
  active, 2 mA pull-down suspended; gpio 17 GPIO 8 mA pull-up active, 2 mA pull-down
  suspended. gpio 18/19 `gpio_i2c_config`. The names are leftovers from the Synaptics
  reference board (the top-level dts still patches a `synaptics@20` node that does not
  exist), but they are what sparrow ran with.
- gpio 30, "TP download mode" (`TP_DLMODE_GPIO`, vd:228, hard-coded, not in the DTS).
  In the reference gpiomux it is CCI_I2C_SCL0 (camera), which sparrow does not have.

## Buffers and I2C transactions

Buffer indices (vd:68-73): `0x20` command (all command writes), `0x40` system command,
`0x80` query/status ("device ready?", "wake up please", "read touch data"), `0xA0`
command response, `0xC0` system response, `0xE0` point info (14 bytes). Only 0x20, 0x80,
0xA0 and 0xE0 are used.

- Write (vd:275-305): one message, `[index, data...]`, i.e. `S 0x8C index data... P`.
  Retried once after 15 ms on failure (I2C_RETRIES 2, vd:229-230).
- Read (vd:240-273): two messages, `{flags I2C_M_NOSTART, len 1, &index}` then
  `{I2C_M_RD, len n}`; the buffer is pre-filled with 0xFF (vd:259) so a failed read
  looks like "busy" / no data.

What goes on the wire: the msm `i2c-qup.c` never looks at `I2C_M_NOSTART` (the string
does not occur in the file) and its functionality is plain `I2C_FUNC_I2C`
(i2c-qup.c:1426). The first message is emitted as `START|addr` then the index byte
(qup_issue_write, :752-760); because the next message is a read to the same address,
the last byte gets no STOP (`rem > 1` → `QUP_OUT_DATA`, :793-794); the read then starts
with `START|addr|1` and `REC n`. So the vendor's read is
`S 0x8C index Sr 0x8D d0..dn-1 NACK P`, exactly the shape `i2c_qup_start(qup, 0x46,
&index, 1, buf, n, ...)` produces in our driver (write entries with no STOP when a read
follows, then START+addr|1, REC). Equivalent. (On a core that honoured NOSTART on a
first message it would be meaningless anyway; Qualcomm's port kept the same flags,
qc:243-255.) Our limits fit: the longest command is 10 bytes (firmware-mode enter,
vd:376), the longest read is 14 (point) / 10 (identify, versions).

## Status byte (0x80)

vd:109-116: bits 2-0 command status, `0` done, `1` busy, `2` error (qc adds `7` = no
connection, qc:113); bits 7-3 point info: `0x80` new point data, `0x08` no new data but
finger(s) still down.

`waitDeviceReady(forever, slowly, probe)` (vd:312-345): reads 0x80 repeatedly while bit
0 is set; up to 50 tries in probe or firmware update, 500 otherwise, unlimited with
`forever`; 1000 ms between tries if `slowly`, 10 ms while `probe_flag` (during probe),
otherwise back-to-back; aborts at once if `enter_lowpower_flag`. Returns true only if
the whole byte is 0 (so "ready with point data pending" counts as not ready, though
callers ignore the result). `i2cRead`/`i2cWrite` (vd:347-357) call it before every
access; the `NoReadyCheck` variants do not. A command is: wait, write to 0x20, wait,
read the response from 0xA0; success replies are two zero bytes.

## Probe and init order (vd:1691-1855)

1. No regulator or reset handling: the rails are always-on from boot and the reset line
   is left as gpiomux set it.
2. `chipIdentifyIT7260(true)` (vd:1632-1673): disable irq, wait ready (probe: 50 x
   10 ms), write `0x20 [0x00]`, wait ready, read 10 bytes from 0xA0, expect
   `0A 'I' 'T' 'E' '7' '2' '6' '0'`, then bytes 8-9: `'5' '6'` = rev BX3, `'6' '6'` = BX4,
   anything else logged and accepted. (The early returns on I2C failure leave the irq
   disabled; harmless since the irq is not requested yet.)
3. If identify fails: "TP download mode" (vd:1730-1753): gpio 30 high, 10 ms, reset
   (gpio 16) low, 60 ms, `gpio_free` (see below), 100 ms, gpio 30 low, 200 ms,
   `TP_DLMODE = true`. Probe carries on regardless. In DL mode most power handling is
   skipped (`!TP_DLMODE` guards) and the upgrade path re-flashes.
4. Input devices: 2 MT slots, ABS 0..`SCREEN_X/Y_RESOLUTION` (vd:1755-1776), a palm
   input device and a "palm" sensors class device (vd:1778-1803).
5. Delayed works, the threaded IRQ (falling), the ASUS mode notifier, sysfs.
6. Reads gpio 30 (vd:1839-1845): if high, `TP_DLMODE = true` ("in tp download mode").
7. Versions are **not** read at probe; only by the sysfs `upgrade`/`status`/`version`
   nodes (chipGetVersions vd:607-643): `0x20 [01 00]` → 10 bytes, firmware version is
   bytes 5-8; `0x20 [01 06]` → 10 bytes, config version is bytes 1-4. The shipped files
   carry fw customer id 5,13 version 00 15 (`it7260.fw` bytes 8-11) and cfg customer id
   7,1 (wren 7,2) version 24 0f (`it7260.cfg` bytes len-8..len-5): a chip upgraded by
   Wear OS should report `fw 05 0d 00 15`, `cfg 07 01 24 0f`.
8. No calibration at probe. `CMD_CALIBRATE 0x13` (`[13 00 autotune 00 00]`, vd:866-870)
   exists behind sysfs `calibration` and the exported `sendCalibrationCmd` /
   `enableAutoTune` (vd:1177-1199), which nothing in the kernel calls. Never needed.
9. Palm threshold (`ChangePalmThreshold`, vd:547-570): `0x20 [21 00 L H]`, response two
   zero bytes. Values used: 0x7000 before entering low power (vd:1280, 2039), 0xA000
   after waking from it (vd:1311, 1568) and whenever a type-0x10 record arrives while
   interactive (vd:1372-1376). The boot value is whatever the config holds.

Firmware upgrade (0x60 enter/exit with `'IT7260' 55 AA`, 0x61 offset, 0x62 write, 0x63
read, 128-byte chunks, config at `0x8000 - cfgLen`, CRC-CCITT check, CRC command
`[1A 09 03]`, reinit 0x6F / 0x0C) is documented in vd:359-603, 712-854. We do not
upgrade.

### The reset line

Every reset in the driver is `gpio_request(16)`, `gpio_direction_output(16, 0)`,
`mdelay(60)`, `gpio_free(16)`, `msleep(50)` (vd:686-690, 985-989, 816-818, 1744-1746).
It never drives the line high. On msm 3.10 `gpio_free` → `msm_gpiomux_put`
(gpio-msm-common.c:206-209), which at refcount 0 writes the `GPIOMUX_SUSPENDED` setting
(gpiomux.c:119-120): GPIO, input, 2 mA, **pull-down**. So the line is active low,
pulled up elsewhere (externally or inside the chip, strong enough to beat the TLMM
pull-down), and the SoC only ever pulls it low. Our draft does the same: output low
60 ms, then input without pull, 50 ms. Driving it high would also be wrong if the
pull-up goes to the 2.85 V rail (TLMM high is 1.8 V).

## Point record (0xE0, 14 bytes)

`struct PointData` (vd:144-168): byte 0 flags, byte 1 palm (Qualcomm calls it
`gesture_id`), then 3 x `struct FingerData` of 4 bytes: `xLo`, `hi`, `yLo`, `pressure`.

- flags bits 7-4 record type: `0x0` touch; `0x1` (Qualcomm: `PD_FLAGS_IDLE_TO_ACTIVE`,
  qc:120) the chip left its idle/low-power state because of a touch, carries no
  coordinates; others are gestures and are dropped (vd:1369-1378). Bit 3 `NOT_PEN`
  (comment says set for pen, clear for fingers; unused). Bits 2-0: finger n valid.
- palm byte bit 0: palm detected.
- Coordinates (readFingerData, vd:1226-1252): `x = xLo | (hi & 0x0F) << 8`,
  `y = yLo | (hi & 0xF0) << 4`; 12 bits. Pressure is `pressure & 0x0F`: 0 none, 1 hover,
  2 light, 4 normal, 8 high, 0xF heavy (vd:162-168).
- Range: the driver reports raw values against ABS 0..320 (wren 0..280) with no scaling
  or axis flip (vd:1773-1776), so the chip reports panel pixels; the config has 0x0140
  at its `a6`/`a7` entries (`it7260.cfg` 0x49-0x4e), likely the x/y resolution.
  Orientation relative to the framebuffer: [U].

### Interrupt handler (readTouchDataPoint, vd:1345-1466)

1. Read 0x80 (no ready check). If the read succeeded and bit 7 is clear: log "called
   when no data available" and return. (If the read failed it carries on.)
2. Read 14 bytes from 0xE0.
3. Non-touch type: drop (0x10 also resets the palm threshold to 0xA000).
4. Palm: if palm bit and not locked and not already reported, and more than HZ/4
   (250 ms, HZ = 100) since leaving low power: lock touch, report `KEY_SLEEP` press and
   release, palm `ABS_DISTANCE` 1/0 if enabled, release both slots (sendPalmEvt,
   vd:1321-1343), and after 30 jiffies (300 ms) unlock unless the display went
   non-interactive meanwhile (waitNotifyEvt, vd:1269-1274). Android turns KEY_SLEEP
   into "go to ambient".
5. Finger: decoded only if `flags & 3`; down if either finger 0 or 1 has pressure >= 2;
   slot n reported down only if its flag bit is set and touch is not locked.
6. Up: no finger with pressure >= 2 **and** palm bit clear → release both slots, clear
   `hadFingerDown`/`hadPalmDown`. With the palm bit set and no finger nothing is
   reported (the palm keeps the lock).

Finger 2 is never used (two slots only).

## Power modes

`CMD_PWR_CTL 0x04`: `0x20 [04 00 mode]` (vd:81-83; qc:75-82): mode 0 active, 1 low
power ("idle": the chip scans slowly and still interrupts on a touch, first record type
0x10), 2 sleep (no scanning; woken by a host read of 0x80). Qualcomm waits 20 ms after
any mode change (qc:770) and enters active mode by reading 0x80, not by a command
(qc:760-764). The sparrow driver writes these without a ready check.

- sysfs `sleep` (vd:1095-1122): sleep = disable irq + `[04 00 02]`; wake = read 0x80 +
  enable irq. Not used by the screen-off path.
- Display non-interactive (ambient; ASUS mode notifier code 0, vd:1202-1222 →
  chipLowPowerMode(1), vd:646-710): release slots, enable irq wake, lock touch, and 500
  jiffies (5 s) later `touchIdleOnEvt` (vd:1276-1291): palm threshold 0x7000, then
  `[04 00 01]` (low power), `chipInLowPower = true`.
- In low power the interrupt goes to readTouchDataPoint_Ambient (vd:1468-1616): the
  first interrupt only unlocks (and takes a wakelock) and re-enters itself; a type 0x10
  record (finger landed while idle) queues exitIdleEvt 5 jiffies later (vd:1584-1588,
  1293-1319), which, unless a palm was sent in the last 800 ms, reports a tap at (1,1),
  holds a 500 ms wakelock and sets the palm threshold back to 0xA000. A touch record
  that goes down and up within 140 ms is also reported as a tap at its position; longer
  touches (moves) do not wake. Any interrupt clears `chipInLowPower` (the chip has left
  low power by itself).
- Display interactive (code 1 → chipLowPowerMode(0)): cancel the idle works; **only the
  first time after boot** (`first_leavelowpower`, vd:680-693) pulse reset (60 ms low,
  release, 50 ms) unless in DL mode or updating; disable irq wake; unlock. No command:
  the chip leaves low power on its own.
- System suspend (vd:2021-2051): lock, enable irq wake, cancel the idle work, palm
  threshold 0x7000 and `[04 00 01]` if not already in low power. Resume only marks the
  driver available (vd:2014-2019).

So Wear OS keeps the controller powered and in low-power idle (mode 1) whenever the
screen is not interactive; it never uses mode 2 on the screen-off path, and never cuts
the rails.

### What our firmware should do on sleep

`touch.h` has no sleep hook and `power.c` does not talk to touch, so the draft leaves
the chip in active mode all the time (it may still idle by itself, depending on the
config). When a hook exists (`touch_sleep(bool)` called by the power policy):

- asleep with tap-to-wake on: palm threshold `[21 00 00 70]`, then `[04 00 01]`, 20 ms;
  the next record is type 0x10 and should be queued as `TOUCH_DOWN` (followed by
  `TOUCH_UP`) so `main.c` wakes the watch; the main loop already ignores the waking
  touch until its UP. Records of type 0x10 while awake stay dropped.
- asleep with tap-to-wake off: `[04 00 02]` (sleep) with the pin interrupt masked;
  palms cannot be seen then, which is fine since palm only puts the watch to sleep.
- awake: read 0x80 (wakes from mode 2, harmless otherwise), palm threshold
  `[21 00 00 A0]`, unmask. The vendor's one-time reset on the first wake is covered by
  our reset at init.
- The MPM wake pin for gpio 17 (BOARD_TOUCH_MPM, still the sturgeon value 8, [U]) is
  armed level-low by `spm.c`; with an edge-type TLMM interrupt that still works if the
  line stays low until the record is read (see below), not if it is a short pulse.

## Interrupt type

The DTS and the driver say falling edge (vd:1823); Qualcomm's port uses level low with
ONESHOT (qc:1934-1935), which only works if the line stays low until the host reads the
record. Which it is: [U] (scope or log on the bench). The draft uses
`TLMM_IRQ_EDGE_FALLING`, acknowledges the pin at the start of a round (so an edge during
the round stays latched and fires on unmask), and has a fallback in `touch_poll`: a line
found low with no round for 50 ms starts one (logged once). That covers an edge missed
at init, after an I2C error, or a level line. If the bench shows a level line, switching
to `TLMM_IRQ_LEVEL_LOW` with the sturgeon ack-then-unmask is the simpler shape.

## 280 x 280 vs 320 x 320

`CONFIG_ASUS_WREN` (set in `wren_*_defconfig`) selects ABS 0..280 (vd:53-59) and config
customer id 7,2 instead of 7,1 (vd:120-126); everything else is the same driver, same
address, same pins. The coordinate range follows the panel through the chip's config,
so a wren build needs `RANGE` 280 (better: a board macro).

## Draft driver decisions (src/input/touch_it7260.c)

- Init: IRQ pin input pull-up; enable L6, L19, LVS1 through the RPM; reset 60 ms low,
  release, 50 ms; QUP5 at 384 kHz (function 3, as sturgeon); wait ready (50 x 10 ms);
  identify (fail → no touch; no download mode, gpio 30 untouched); versions logged;
  palm threshold 0xA000; falling-edge pin interrupt.
- Chain in interrupt context, as on sturgeon: mask + ack pin → read 0x80 (1 byte) → if
  bit 7, read 0xE0 (14 bytes) → decode → queue → unmask.
- One finger: the first valid finger with pressure >= 2; coordinates scaled from 320
  to `fb.width`/`fb.height`, clamped.
- Up: a touch record with no such finger and the palm bit clear.
- Palm: on the palm bit's rising edge, a `TOUCH_UP` if a finger was down, then
  `TOUCH_PALM`; fingers are suppressed until a record with neither palm nor finger. The
  vendor's 250 ms after-wake palm guard is not needed without a low-power mode.
- Non-touch records (types 1-15) are dropped.

## Bench unknowns

- Whether the line is edge or level; whether INT rises when 0xE0 is read.
- That the reset line has a pull-up and the release-to-input reset works; how long
  after reset the chip answers (vendor waits 50 ms and then polls).
- Which of L6/L19/LVS1 the chip actually needs, and that RPM enables them at the right
  voltage without a voltage request (sturgeon relies on the same for L19).
- Chip revision (BX3/BX4) and the versions in the chip (upgraded by Wear OS or not).
- Coordinate orientation and range (0..319 or 0..320) against the framebuffer.
- The record type that arrives when the chip idles by itself while active, and whether
  the chip idles at all in mode 0.
- The palm threshold units and whether 0xA000 is right for us; the config default.
- gpio 30's level at boot (if high the chip may be in download mode).
- The MPM pin for gpio 17.
