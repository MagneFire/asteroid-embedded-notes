# Native triangle path: the replayed scene

`src/gpu/sgx_draw.c` draws triangles on minnow's SGX530 without vendor code: it sets up, at the
GPU addresses the vendor's driver used, the whole GL scene that driver built for a 320x320 pbuffer,
from data recorded off the driver, and per frame rewrites only what differs. Data:
`src/gpu/sgx_scene_data.[ch]`, generated by `tools/sgx/mkreplay.py` from the glrec.py recordings.
Host test: `tests/sgx_draw_test.c`. Console: `sgx tri`.

## What is replayed

- **Allocation table**: the GL context's 82 allocations in the recorded order (heap, size, alignment,
  flags, recorded address, kind). Kinds: 65 user allocations, 16 sync data blocks (40 bytes, heap 8,
  made by the kernel right after each allocation without NO_SYNCOBJ), 1 HW render context (64 bytes,
  KernelData, made at REGISTER_HW_RENDER_CONTEXT). `sgx_draw_setup()` allocates them with
  `sgx_alloc()` after `sgx_start()` and refuses when any address differs from the table. They continue
  each heap after the init image, as in the recordings. Total about 5.4 MiB of the 16 MiB pool
  (parameter buffer 3.9 MiB, pbuffer 400 KiB, rings). One deliberate size change: the vertex buffer is
  4032 bytes (56 triangles) instead of the recorded 96; the next General allocation stays at
  0x000e2000 for any size up to 4 KiB (mkreplay re-runs the placement policy over the whole table).
- **Image**: `tri_read`'s memory at its first kick, as runs of non-zero words, a run repeated at a
  constant step stored once (the MTE-copy ring holds one 32-byte program 400 times). Left out because
  the native code writes them: everything below under "generated", the kernel's words, and two tables
  it builds (parameter-buffer page links `next | prev << 16`, 989 entries; the 1024-entry identity
  index table). mkreplay checks that the runs give back exactly the image less those words.
- **Templates**: the TA command's user-written words (20), the render details' 34-word 3D register
  block, the 7-word end-of-scene VDM block, both kicks' status lists, blend off/on words.

Size: 53 runs + 605 words = 3056 bytes of image; 4884 bytes for all tables in the firmware
(`arm-none-eabi-size`: text 4884). `sgx_draw.c` is 3.2 KB of code. The recorded image has 972
non-zero 64-byte blocks (60 KiB); the MTE-copy ring (50 KiB) and the two generated tables (6 KiB)
are most of it.

### The kernel's part

Done as `sgxkick.c` / `sgxutils.c` do it, checked against the lab's fake kernel (which follows them):

- HW render context +8: the page directory's physical address in directory-list format, which for the
  SGX530 (no 36-bit MMU, `SGX_MMU_PTE_ADDR_ALIGNSHIFT` 0) is the address unshifted: `mem.phys`, the
  one directory the firmware uses for the kernel and the client heaps alike.
- Per kick, shared part: TA/3D dependency (last kick: sync 0x0d801000's write-pending value and
  write-complete address, then pending +1), status counts and pairs, source count 0; on the first kick
  the HW device sync list 0x0f0ad000 (count 1, the surface sync 0x0d809000's read/write/read2 values and
  addresses, write pending +1); READY last. No barrier between: everything is uncached and `kick()`
  ends with `dsb` before the kick register.
- Status values: sequence words as the driver counts them (0x0d811000 = kicks so far, 0x0d80a000 =
  scenes so far); ring words the recorded values (first kick VDM 132, vertex 96, index 16, PDS
  vertex 444, 0, MTE copy 384, PDS pixel 288, tile store 120; last kick VDM 160).
- Kernel CCB command: TA handler 0x1ec (the init recording's host kick address for TA), cache control,
  data = {0, HW render context, 0, 0, 0, 0} as in the recorded `sCommand`. Cache control: PT|PD (3) on
  the first TA command after setup and after mapping a new target (the kernel's MMU code sets
  `INVAL_BIF_PT` when it maps pages and `INVAL_BIF_PD` when it adds a page table), 0 otherwise. No
  data-cache invalidate is ever asked, so BRN 28889's separate invalidate does not arise.
- Not done, as in the lab: the kernel's `ui64LastWrite` (kick counter) in the surface sync's data;
  kernel bookkeeping the microkernel is not known to read.

## Ring policy: frame one's place, every frame

The vendor appends each frame to its rings (VDM, vertex, index, PDS vertex, MTE copy, PDS pixel,
tile-store code) and relocates everything that points into them. The native code rewrites frame one's
content at frame one's offsets every frame, after the previous frame's render has completed. Reasons:

- Frames are serialized: a frame starts only when the last scene is rendered and its details and
  sync-list access words are released, so nothing still reads the old data.
- Appending needs every ring-relative word relocated: in tri_read2's frame 2, VDM PDS offsets, index
  addresses, MTE-copy entries pointing into the PDS vertex ring, the background PDS offset in the
  command (+0x10), the pixel-event PDS offset in the details (+0x54), the stream pointer, the status
  values, and the driver even emitted the vertex PDS program into the ring instead of its cached
  block. Each would be decoding work and a source of error, for nothing a serialized renderer needs.
- Ring wrap and link words (G:0x3f64) never arise.

The TA command ring is the exception: it is a real producer/consumer queue with the microkernel, so
commands are appended, 0x540 bytes each, the write offset modulo 0x10000 (the 0x688-byte overrun
lets a command cross the end, as the driver allows). Frame k's commands are therefore at the same CCB
offsets as the vendor's frame k.

What a frame must match: frame 1 equals `tri_read` byte for byte (kick 0 and 1). Frame 2 equals
`tri_read2` frame 2 in every word that does not depend on a ring offset; those words equal frame 1's
(list under the host test). Two things a second frame changes that are not offsets, both taken over:

- **The MTE-copy toggle.** G:0x3bfa0 builds an MTE-copy launch's second word as
  `(toggle + 0x2000) | 0x28200 | (data_bytes >> 4) << 26 | (state_words + 3) >> 2` and flips
  `toggle` (context +0xf3c) after every launch. Three launches a frame, so frame k starts with
  toggle (k-1)&1. The toggle lands on bit 0, ORed with the word count; the second and third launches
  have odd counts (3, 5), so only the first (count 2) shows it: 0x0c02a202 in odd frames, 0x0c02a203
  in even ones, as tri_read2 and tri2 record. Whether the hardware needs the alternation is not
  known; the native code keeps it.
- **First-scene bit**: flags A 0x10 only on the surface's first scene (0x71 vs 0x61).

`tri2` (two glFinish frames without readback) is not a reference for frame 2: on a pbuffer glFinish
does not end the scene, so its second kick is a middle kick of the same scene (flags A 0x60) and the two
frames would render as one. The native path never makes middle kicks; each frame is a whole scene.

## Render target

`tri_read_gap` (glrec.py `--general-gap 0x100000`) moved the General heap, the pbuffer first, 1 MiB
up. Every word that moved with the pbuffer's address:

- tile-store programs in the CBUF8 ring 0x0f400000: the PBE word 3 immediate (register selector 3) at
  +0x18 and +0x58, one per program (two programs);
- the PDS pixel ring 0x0dc08000 +0xc8: a plain address in the background program's data, the texture
  the background object can load the old target from (ta-path G:0x7a64).

No other word depends on the target. `sgx_draw_target(addr)` writes the immediate with
`sgx_set_constant()` (the encoding of `sgx_image.c`: low 21 bits in word 0, bits 21..31 in word 1's
0x3f1f0 field, other bits kept) and the plain word `addr & ~3`. The stride (PBE4 = 159) and extent
(PBE1 = 0x13f13f) stay: the target must be 320x320, rows of 1280 bytes. `sgx_draw_map(phys, size)`
maps memory outside the pool (the frame buffers) at the next General address after the scene, with
R|W|NO_SYNC as the pbuffer has, at most four mappings.

**Pixel format**, settled from the recording: the pbuffer's PBE word 2 is 0x00008000, format nibble
0, which in the driver's table (G:0x65128) is ARGB8888/XRGB8888, not ABGR8888 (0x10000000). The GPU
writes 32-bit words 0xAARRGGBB: in memory B, G, R, A. That is the layout of the display's XRGB8888
frame buffer (DSS GFX format 0x91), so frames go into `display_backbuffer()` unchanged, the alpha
byte ignored by the DSS. The clear colour is packed the same way (0xff4080bf for 0.25, 0.5, 0.75, 1).
Byte-order RGBA targets (`gpu_target.rgba`) are not offered: that needs PBE format 0x10000000, which
no recording shows; a recording of a pbuffer with an ABGR8888 config (glenv's WSEGL config list) would
settle it. Channel order on the panel is the first thing the watch shows (checklist).

## What only the watch can show

- That the microkernel takes the TA command at all (kernel CCB, TA CCB read offset moves).
- Completion: which status words and syncs the microkernel really writes, and when: the native wait
  for the first kick wants the TA CCB read offset caught up and the kick-sequence word (0x0d811000) =
  kicks; for the last kick also the scene word (0x0d80a000) = scenes, both access words 0, and both
  syncs' write-complete = pending. The lab's completion is an assumption on all of these.
- Whether the microkernel decrements the RT dataset counter (0x0f0ae000) on completion; the native
  code increments what is in memory, which is right either way only if nothing else writes it.
- Real parameter-buffer, region-header, tail-pointer and RTDATA mutation across frames; the native code
  never resets them (only the words the driver itself rewrites at a new scene).
- Whether replaying frame one's ring content each frame is accepted, and whether the MTE toggle matters.
- Pixel colour order, orientation (GL's bottom-left origin vs the panel's first row), the alpha byte.
- Instruction caches: blend on/off rewrites fragment code between frames; the driver writes new code
  to new addresses instead. If a blend change does not take, the code cache is the suspect.
- Kick-to-completion time.

## Open problems

- Restarting the GPU (`sgx off`, then `sgx tri`) keeps the scene memory and counters but restarts the
  microkernel; untested, and the TA CCB offsets in the HW context may disagree with a fresh
  microkernel. Test from a fresh boot.
- No parameter-buffer growth or out-of-memory handling: a scene must fit the 2 MiB usable PB.
- Byte-order RGBA targets, textures (blocked on the transfer queue), other shaders: not recorded.
- The first kick's 3D status list is written as recorded; whether the microkernel writes 3D statuses
  of a non-last kick is not known (harmless: same values as the last kick's).

## The scene moved to mix's addresses

The multi-draw recordings (`mesh*`, `mix*`) are made with the gralloc transfer context, whose 67
allocations come before the GL context's and move it (General +0x40000, PixelShaderUSSE +0x3a000,
PDSPixel +0x8000, KernelData and the sync heap too). A byte comparison needs the native scene at those
addresses, so the replayed scene is now `mix`'s GL context (both programs compiled), not `tri_read`'s:

- 88 allocations: mix's GL context; each heap's run of transfer-context allocations becomes one hole
  (allocated, never written) that keeps every later address; the hole in General (0x1000, 256 KiB) is
  the native vertex buffer (`SGX_SCENE_VERTICES`). The two textures and their sync objects (allocated
  last, at first draw) are left out: textures are the caller's memory.
- The identity index table (0x126000) is one page now: 2048 vertices a draw (`SGX_DRAW_MAX_VERTS`).
- The image is mix's memory at kick 0 less what the native code writes: the VDM, PDS vertex, pixel and
  pixel-code rings past the clear's part (prefixes 0x40, 0xe0, 0x120, 0x60), the MTE-copy entries but
  for their code (every one of the 400 entries has its 8 code words from the start; the native code
  must not clear them), the cached flat vertex program's two stream addresses, the per-frame sites,
  the kernel's words. mkreplay checks the image is also mesh's, tri_tq's, tri_read_tq's, mix_minus',
  mix_swap's and mix_back's wherever the native code does not write (but the textured code, below).
- To keep the old scenes comparable, the tri scenes were recorded again with the transfer context
  (`glrec.py tri_read_tq ...`, the `_tq` names now in glrec.py; `--general-gap 0x100000 tri_read_tq`).
  Their commands are mix's, their rings' prefixes are mix's; only the VBO/index table place and the
  textured code differ.

Size: tables 5.3 KB (`sgx_scene_data.o` text), image 49 runs + 560 words = 2828 bytes; `sgx_draw.o`
5.7 KB, `sgx_compose.o` 5.4 KB + 6 KB bss.

## The multi-draw recipe as implemented (`sgx_draw.c`)

A frame is a clear colour and up to 64 draws; each draw is flat (x, y, r, g, b, a) or textured
(x, y, u, v) from a GPU address, at most 2048 vertices. Every frame is written at frame one's place
(ring policy above), the rings in this order per draw, each item 32-byte aligned:

| Draw | PDS vertex ring | MTE-copy | pixel ring | pixel code | VDM |
|---|---|---|---|---|---|
| flat, first | 18-word block (ISP word 01d00200 / 03d00200 with blend; copied as 25 words), vs-constants 0x40, vs-descriptor 0x40 | entry, copy 0x01000018 / dest 0x00201a1a | - | - | MTE launch, vs launch, index list -> cached program 0x0e81d000 (its words 0 and 2 = vertices, vertices + 8) |
| flat, after a textured draw | vertex program 0x60 (stride 0x18, 0x281a), 9-word block, vs-constants, vs-descriptor | copy 0x01000008 / 0x0020101a | - | - | MTE launch, vs launch, index list |
| textured | vertex program 0x60 (stride 0x10, 0x2b1a); 9-word block after a flat draw, else 4-word block (0x00600003 / 0x00200b1a); vs-constants + descriptor only when the previous draw was flat or had another texture | entry | secondary: constants 0x40 (alpha at +0x24), descriptor 0x40 | texture program 0x40, once per texture a frame, first use first | MTE launch, [vs launch], index list |

- Launch word: `0x0c02a200 | toggle | (n + 3) >> 2`, n the block's words (18, 9, 4 give 5, 3, 1, all
  odd, so the toggle shows only in the clear's first launch, VDM+4, whose count is 2). The toggle is the count of MTE-copy
  launches so far, kept across frames (and across GPU power-offs, as the driver's context keeps it):
  mix2 (6 launches a frame) starts frame 2 with 0, tri_read2_tq (3) with 1. No recording tells
  "launches" from "launches of the draws only" apart (same parity in both), nor checks a toggle in a
  draw's launch.
- Every textured draw gets a new pixel secondary program, state block and MTE launch, as mix_plus has
  for a draw whose uniform was set again with the same value; mix_same (uniform not set) leaves them
  out, which the native path never does: mix_same is not compared.
- Status values = ring ends (TA: VDM end incl. the end block, PDS vertex end of the last item
  unrounded, MTE end; 3D: pixel ring end); the others recorded.
- Texture words: sampling 0x03fe0090 (nearest) / 0x03fe1490 (linear, from quad_linear), size
  `0x8d000000 | (w-1) << 12 | (h-1)`. Refused: power-of-two sides (the driver uses the twiddled log
  form there), widths not a multiple of 32, addresses off a page, textured draws without blending,
  a textured first draw, a flat draw after a flat one, flat blending unless the first draw is the only
  flat one (blend changes the flat program's code, shared by every flat draw). None of these is recorded.

## The compositor (`src/gpu/sgx_compose.c`)

The draw.h / a3xx.h calls on minnow are a dispatcher: each frame goes to the GPU while it is wanted
(started at boot by `gpu_init`, by `sgx ui on`) and running, else to `soft.c`, whose functions are now
`soft_*` (`soft.h`; behaviour unchanged, `soft_test` passes; its pool is page aligned now so the GPU can
map it). paint.h stays on the CPU. Mapping:

- Target: both frame buffers (FB_BASE, 1 MiB) mapped once; the target is set per frame. Must be
  320x320, pitch 1280, not rgba; anything else is drawn by the CPU.
- Clear: black 0xff000000 (what turn_frame leaves outside a turned picture).
- Every position y-flipped (GL's origin is the bottom row); with a turn, positions are turned first
  (draw.c's formula), the caller's vertices are left alone: gpu_draw_turn_vertices only marks which
  ones, so the CPU can still draw the frame from them.
- The mesh: the frame's first gpu_draw_triangles with blending off -> the flat draw, x, -y, r, g, b, a.
- Layers (gpu_draw_layer_parts/at/layer): one textured draw a call, six vertices a rect, UVs =
  rect / size, alpha byte round(a * 255), read in place from UI_LAYER_BASE (7 MiB mapped), 320x320,
  pitch 1280: exactly the recorded 320x320 RGBA texture (format 0x0d, bytes R, G, B, A = the layers').
- gpu_draw_layer_round: 64 triangles from the centre to flatmesh_round_edge, as draw.c.
- Indicators and any texture up to 32x32: copied into a slot of the compositor's own 320x320 texture
  (General, 400 KiB, uncached), drawn with UVs inside the slot. A linear 32x32 texture in the GL
  program is not recorded: quad_tex's 32x32 has the power-of-two word 0x0d050005 (twiddled layout,
  which no recording shows as data, the blit not being executed); the upload blit samples its staging
  buffer linearly at 32x32 (texprobe: A 0x80020018, B 0xec01f01f), but in the blit's own program,
  whose texture words are another form. What would settle it: a recording of a GL draw from a 32x32
  EGLImage on a linear gralloc buffer (the lab's gralloc would have to allocate buffers), or a watch
  test of the explicit-size word 0x8d01f01f on a 128-byte-pitch buffer. Until then the closest
  recorded variant is used: the layers' 320x320 words, the icon in a 32-pixel slot, only the UVs differ.
- Triangles after the mesh (the app's background, blended while it fades): a textured draw from a
  palette in rows 32.. of the own texture, a texel per triangle (its first vertex's colour, as soft.c
  takes it), alpha 1: premultiplied over gives colour + target * (1 - a). This avoids a second flat
  program and flat blending in a frame that also has the opaque mesh, neither recorded. Not recorded
  either: a flat draw right after the mesh (the background at full alpha), which this also covers.
- gpu_alloc: soft's pool, mapped for the GPU (192 KiB); nothing reads it there today (indicators
  are copied), but GPU-readable as required.
- Caches: gpu_draw_cpu_sync cleans and invalidates the frame buffer before and after (both times: the
  CPU may have drawn the frame instead); frame.c cleans the damaged rows of layers (have_gpu is true
  on minnow); power.c's ambient path cleans what it repaints; vertices, palette and slots are written
  into the uncached pool. Texture cache: nothing invalidates the GPU's texture cache between frames;
  the microkernel is assumed to do it at each 3D start, as it must for SurfaceFlinger's CPU-written
  buffers (watch: stale layer content would show).
- Failure: a frame the GPU path does not take (more than 64 draws, a size it cannot place, no
  vertex room) is drawn by the CPU, logged once. A frame that fails on the GPU (kick not done in 1 s;
  the watchdog is fed while waiting) logs one line `sgx: <why>; the CPU draws from now on`, the GPU is
  reset and powered off at once (sgx_halt: no POWER command to a hung microkernel), and the frame is
  drawn again by the CPU from the kept calls (up to 48 calls, 128 rects); every later frame and wake
  stays on the CPU.
- `sgx: N frames, geometry X us, render Y us` once a second while frames are drawn on the GPU; the
  `frame:` line is frame.c's on both paths (mesh = the mesh call, layers = stack_compose, end =
  gpu_draw_end incl. the GPU's work and the cache maintenance, flip).

## Power

The scene stays in GPU memory across a power-off; nothing is rebuilt. The vendor's kernel does the
same: its active power management (sgxpower.c) sends the POWER command and cuts the domain, and on
power-up SGXInitialise runs the scripts, sets the kicker to 0, resets the init status and kicks the
microkernel: exactly sgx_start, no image rebuild, no client context touched, no cache-control bits
added. The render context, rings, counters, launch toggle, RT index and CCB offset carry on. sleep:
frame_sleep -> gpu_suspend -> sgx_stop; wake: frame_wake -> gpu_init -> sgx_start (the image is built
only the first time). The host test's power-cycle scenario covers that a frame while off is refused
without touching the scene and that the next frame equals mix2's frame 2.

## Failure state machine (`sgx.c`)

- One forced path, `quiesce()` (`sgx_halt()` from outside), ends every failed transition: power-on,
  library/image build, reset, init timeout, query timeout, the stop handshake (POWER command,
  POWER_OFF_COMPLETE, clock gating), and every frame failure in the compositor or `sgx tri`. It works
  whatever `running` says: IRQ line masked; if the domain is up (`powered`, set only after PWSTST shows
  ON), the OCP interrupt is disabled, outstanding BIF requests get 10 ms (`DRAIN_US`, watchdog fed) to
  drain, then SOFT_RESET = all while the clocks are still on, the deinit script, and then clocks and
  domain off. Without power it only cuts the clocks, with no SGX register access. Opus R3: a reset or
  clock cut under an OCP transaction can wedge L3; the vendor drains through its dummy directory in
  recovery, the short drain here is the bounded version of that.
- After a failure `sgx_failed()` is true and stays so until a start works. `reset_once` is cleared, and
  the next `sgx_start` builds everything again: the library is read again, the pool re-initialised
  (`sgx_mem_init` wipes it page by page as it allocates), the image, page tables, reset pages, cache
  bits and counters made anew, and `sgx_generation()` goes up. `sgx_draw.c` compares the generation in
  every entry point and starts the scene from scratch when it changed (`forget()`: ready/stuck, CCB
  offset, kick/scene counters, RT index, launch toggle, target, maps, vertex arena); the compositor
  drops its aux texture and maps on the same signal. A clean stop and start keeps image and scene as
  before (vendor behaviour, see "Power").
- Nothing retries by itself: `gpu_init` (boot and every wake) starts the GPU only if it was turned on
  and has not failed since. One log line per failure: the specific reason, then once
  `sgx: off after a failure; sgx ui on starts it again from scratch`. The explicit retries are `sgx ui
  on`, `sgx` and `sgx tri`.
- Register waits feed the watchdog. The whole reset has one deadline, `RESET_US` = 200 ms (the bark is
  at 3 s), shared by every BIF invalidate in it; an invalidate that times out, or faults still pending
  after the drain (64 at most), fail the reset and so the start. `dsb()` after the page-table stores of
  the fault drain (both setting and clearing) before the register writes that use them (Opus R5).
- The command-queue-full wait feeds the watchdog too. Worst case of a failing start is now about
  100 ms (power) + build + 200 ms (reset) + 1 s (init, fed) + 10 ms drain.

## Compositor (`sgx_compose.c`) and frame.c

- **The GPU is not started at boot** (Opus R6/B1, for the first watch session). The switch is
  `#define AT_BOOT false` near the top of `src/gpu/sgx_compose.c`; `true` makes `gpu_init` start it at
  boot again. Until `sgx ui on`, every wake leaves it off too (the boot state counts as "off by hand").
- Refusals (Opus G3, Sol F2): a frame the compositor's own checks refuse, or that `sgx_draw_frame`
  refuses before anything reaches the GPU (`sgx_draw_refused()`), is drawn by the CPU for that frame
  only; the GPU stays on and the next frame goes to it. Each refusal reason is logged once (up to 8
  kinds): `sgx: a frame the GPU does not take, drawn by the CPU: <reason>`. Every GPU frame starts with
  `sgx_draw_discard()`, so the vertices of an abandoned frame are given back.
- A start that fails at any stage (start, setup, aux allocation, a map) halts the GPU (`turn_on`).
- A frame failure: `sgx: <reason>; the CPU draws until sgx ui on`, halt, CPU until `sgx ui on`.
- A lost frame (not drawable on the GPU and too many calls to replay): frame.c then drops the
  compositor for good (`have_gpu = false`), so the compositor stops the GPU at once (`sgx: a frame
  lost; the GPU stays off`) and refuses `sgx ui on` afterwards (logged), since nothing would use it.
- Sleep (Opus G1): `frame_sleep` now calls `gpu_suspend` even when `have_gpu` is false, under
  `#ifdef SGX_BASE` so the Qualcomm image is unchanged. That covers the GPU started from the console
  after frame.c dropped the compositor. The always-on face does not touch the GPU: `ambient_draw` is
  `ui_render` + `display_flip`, and display_minnow.c has no GPU calls; a `frame_draw` while asleep
  would go to the CPU anyway because `gpu_draw_begin` checks `sgx_running()`.
- A failed stop on sleep halts (above) and keeps the CPU after waking (Opus R4).

## Ordering (Sol R1)

## Data-cache invalidate switch (Opus R1, Sol R2)

`sgx inval on|off` (default off; `sgx inval` shows it) ORs `SGXMKIF_CC_INVAL_DATA` (8) into every
frame's first kick. BRN 28889 (sgxerrata.h lists it for SGX530 rev 1.2.5): the vendor never sends
DATA together with PT/PD; when both are pending it sends them in a PROCESS_QUEUES command of their own
and polls `HOST_CTL.ui32InvalStatus` for `BIF_INVAL_COMPLETE` (sgxutils.c:325). Chosen here, the
simpler safe one: `command()` in sgx.c never puts DATA in a command that carries PT/PD; it holds DATA
back for the next command. In practice that only happens on the first frame after a new mapping or
allocation (setup, the compositor's maps), whose DATA then goes with the second kick (before the 3D
render, after the TA). The round trip would need a command type and a host word never exercised
natively, for no gain in this test. Whether INVAL_DATA also covers the USSE instruction cache and PDS
code is unverified.

## `sgx tri` (Sol B2, Opus G2)

- `sgx tri [rrggbb]`: the ground colour is optional (default blue-grey 4080bf); the triangle stays red.
- It maps the whole FB_BASE region (FB_SIZE, both buffers) once, the same region the compositor maps,
  so repeated runs find the map again instead of using up the four slots.
- A failure after submission logs the reason and the state, halts the GPU, and only then invalidates
  the buffer. A refusal (nothing sent) stops a GPU that `sgx tri` started itself; so does a setup/map/
  vertex failure.
- After a frame it logs both buffers: `sgx: buffer N[ (this frame)]: ground XXXXXXXX, triangle
  YYYYYYYY` (row 160 col 4, and row 200 col 160), after clean+invalidating each.

**Two-buffer check (do this before `sgx ui on`).** `sgx tri 00ff00`, then within its 10 s hold
`sgx tri 0000ff` (display_flip alternates, so the second run draws into the other buffer; after the
hold the CPU's frames flip too, and "(this frame)" says which buffer a run used). After the second run the
log must show the first run's buffer with ground `ff00ff00` and the second's (this frame) with ground
`ff0000ff`, both with triangle `ffff0000`. If the second run's colour landed in the first buffer, or
"this frame" still holds the old picture, the tile store ran stale code (Opus R1 3: keep one tile-store
copy per buffer). Then `sgx inval on` and repeat. `shot` reads the front buffer, i.e. the buffer of the
last run.
